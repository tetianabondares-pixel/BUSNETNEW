# Задача: подтверждение заявок и создание реальных бронирований только администратором

## Цель

Разделить текущую заявку пассажира и реальное бронирование у перевозчика:

- вошедший пассажир может отправить заявку BUSNET;
- заявка сохраняется как `bookings.status = 'pending'` вместе с пассажирами;
- только уполномоченный администратор может подтвердить заявку;
- при подтверждении система создаёт реальное бронирование у AL-TRANS и сохраняет `provider_booking_id`;
- статус `confirmed` выставляется только после успешного ответа AL-TRANS.

Не считать существующее создание строки `bookings` реальным бронированием у перевозчика: текущий `create-booking` создаёт только pending-заявку и не вызывает API создания брони AL-TRANS.

## Подтверждённое текущее состояние

- `altrans-adapter` имеет операции `search-trips` и `create-booking`; последняя сейчас повторно ищет рейс и создаёт `trips`/`bookings`/`booking_passengers` в Supabase, но не вызывает AL-TRANS booking endpoint.
- Пассажирская форма вызывает эту операцию и показывает заявку как ожидающую подтверждения администратором.
- В админ-панели действие «подтвердить» сейчас вызывает `public.update_booking_status`, который меняет статус в базе на `confirmed`; он не создаёт бронь у AL-TRANS.
- RPC `update_booking_status` уже разрешает менять статус только ролям `super_admin` и `admin`.
- В `bookings` есть поле `provider_booking_id`; в `booking_passengers` хранятся данные пассажиров.
- `expires_at` у новых заявок сейчас `null`.

Перед работой проверь актуальные версии deployed Edge Function, миграций, RPC и frontend-кода — не считай это описание более авторитетным, чем текущее состояние проекта.

## Требования

### 1. Сохранить подачу заявки пассажиром

- Не добавлять проверку `admin_profiles` в пассажирский endpoint создания заявки.
- Не блокировать пассажирам возможность отправить заявку.
- Сохранять текущие проверки авторизации, принадлежности данных и валидации пассажиров.
- Не вызывать реальное создание брони у AL-TRANS на этапе подачи заявки.
- Ясно называть результат «заявкой», а не подтверждённым билетом/бронированием.

### 2. Создать серверную операцию подтверждения администратором

- Добавить отдельную защищённую операцию, например `confirm-booking`, в `altrans-adapter` либо эквивалентный серверный механизм.
- Принимать идентификатор существующей pending-заявки; не принимать от браузера произвольные суммы, `provider_trip_id`, состав пассажиров или роль для подтверждения.
- Получать пользователя из проверенного Supabase JWT и проверять в `admin_profiles`, что его запись активна и роль входит в `['super_admin', 'admin']`.
- Выполнять проверку роли на сервере для каждого вызова. Не полагаться только на скрытие кнопки в React.
- Загружать заявку, исходный trip и связанные `booking_passengers` из Supabase на сервере.
- Разрешать подтверждение только для `pending`. Повторный запрос для уже подтверждённой или отменённой заявки не должен создавать вторую бронь.
- Сохранять действующее `verify_jwt`; не открывать функцию для `anon`.
- Ключи AL-TRANS и service-role использовать только на сервере.

### 3. Сначала подтвердить фактический API создания брони AL-TRANS

- Найти и подтвердить официальную/фактическую операцию AL-TRANS для создания брони, формат её запроса, обязательные поля, формат ответа и правила идемпотентности.
- Не угадывать endpoint, названия полей, значения payment mode, формат пассажиров и не считать `search_trips` созданием брони.
- Не отправлять API-ключ, service-role key, JWT или персональные данные в отчёты и логи.
- Если endpoint или контракт создания брони не подтверждён, **остановить реализацию реального подтверждения**. Не менять статус на `confirmed`; вернуть понятную серверную ошибку и предоставить обезличенный перечень недостающих сведений.
- Использовать sandbox/test credentials, если AL-TRANS их предоставляет. Не создавать живую бронь в production во время проверки без отдельного разрешения владельца проекта.

### 4. Повторно проверить рейс и цену перед вызовом провайдера

- Перед реальным подтверждением заново получить актуальный рейс у AL-TRANS и проверить соответствие `provider_trip_id`, маршрута, даты, числа пассажиров и доступности.
- Сравнить актуальные цену/валюту с сохранённой заявкой. Если цена изменилась, не создавать бронь автоматически и не списывать/подтверждать новую сумму; вернуть конфликт, требующий решения администратора/пассажира.
- Использовать актуальные данные пассажиров из `booking_passengers`, проверив необходимые поля перед отправкой провайдеру.
- Не включать в логи полные имена, телефоны, email, документы, токены или содержимое заголовков.

### 5. Обеспечить безопасный переход состояния и идемпотентность

- Не допускать двух параллельных подтверждений одной заявки.
- Использовать атомарную блокировку/claim заявки или другой проверенный механизм конкурентного доступа.
- Не считать одного `SELECT ... FOR UPDATE`, выполняемого в транзакции, достаточной защитой, если внешняя HTTP-операция происходит вне той же транзакции.
- Повтор после таймаута должен использовать подтверждённый ключ идемпотентности провайдера либо безопасную сверку существующего бронирования, чтобы не создать дубликат.
- Записывать `provider_booking_id` из успешного ответа AL-TRANS.
- Переводить заявку в `confirmed` и ставить `confirmed_at` только после успешного создания брони у провайдера и сохранения результата.
- При ошибке провайдера не оставлять заявку в ложном `confirmed`. Зафиксировать безопасный технический результат, позволяющий администратору понять, можно ли безопасно повторить попытку.
- Если атомарность между AL-TRANS и PostgreSQL не обеспечивается, явно обработать частичный сбой и описать процедуру сверки/повтора; не маскировать его успехом.

### 6. Ограничить ручное изменение статуса в админке

- Перепроверить текущий `update_booking_status`: сейчас он способен отметить заявку как `confirmed` без вызова AL-TRANS.
- После добавления настоящего подтверждения убрать/запретить прямой переход `pending -> confirmed` через этот общий RPC. Переводить в `confirmed` только через серверную операцию подтверждения.
- Сохранить административное право отмены/возврата согласно текущим правилам; не менять несвязанные переходы статусов.
- В админ-интерфейсе показывать понятные состояния: ожидание, подтверждение в процессе, подтверждена у AL-TRANS, ошибка подтверждения, отменена.
- Успех UI показывать только после серверного успешного результата.
- Записывать аудит действия администратора без чувствительных данных.

### 7. Срок действия заявки

- Сейчас `expires_at` у pending-заявки равен `null`.
- В рамках этой задачи **не вводить срок истечения и не задавать произвольный TTL**.
- Не считать `null` истёкшим сроком. Не добавлять автоматическое удаление или автоматическую отмену заявок.
- Если для работы AL-TRANS нужен максимальный возраст заявки, остановиться и запросить утверждённое бизнес-правило до добавления TTL.

## Миграции и изменения схемы

- Сначала определить, можно ли реализовать задачу текущими полями (`provider_booking_id`, `status`, `confirmed_at`, `audit_logs`).
- Не добавлять новые таблицы/колонки/статусы без доказанной необходимости.
- Для блокировки параллельного подтверждения можно предложить минимальное изменение схемы только если без него не получается надёжная идемпотентность. До применения миграции представить её отдельно и запросить разрешение.
- Не менять ownership, RLS или grants шире необходимого.

## Проверки и критерии приёмки

1. Авторизованный пассажир может создать pending-заявку, но не может вызвать подтверждение.
2. Пользователь без JWT и пользователь с неактивным/недопустимым admin role получают отказ в `confirm-booking`.
3. Активные `super_admin` и `admin` могут инициировать подтверждение pending-заявки.
4. Неизвестный/отменённый/уже подтверждённый ID не создаёт вторую бронь у AL-TRANS.
5. Проверки рейса или цены не пройдены — внешнее создание брони не вызывается, статус остаётся не `confirmed`.
6. Ошибка AL-TRANS не даёт ложный статус `confirmed`.
7. Повторный запрос/параллельное нажатие не создаёт дубликат у провайдера; механизм проверен на sandbox или безопасными тестами.
8. При успешном подтверждении сохраняются provider booking reference, `confirmed_at`, ожидаемые суммы/валюта и запись аудита.
9. Админ-интерфейс использует новый серверный endpoint для подтверждения, а общий RPC не может обойти его.
10. Все существующие passenger request, поиск, отмена и админ-списки продолжают работать.
11. Запустить существующие тесты, typecheck/build и подходящие интеграционные тесты; отделить прежние ошибки сборки от ошибок, добавленных этой задачей.
12. Не выполнять реальное production-подтверждение для теста без отдельного разрешения.

## За пределами задачи

- Не менять логику выбора одного рейса и парсинга остановок AL-TRANS.
- Не включать создание брони у провайдера в пассажирскую заявку.
- Не вводить срок истечения заявок.
- Не выполнять production-деплой, если не подтверждён контракт AL-TRANS или проверки не прошли.
- Не выдавать неподтверждённую заявку за билет.

## Итоговый отчёт

Сообщить:

- какие файлы, функции и миграции были изменены;
- какие роли имеют право подтвердить заявку;
- как реализованы повторная проверка цены, защита от гонок и повторов;
- фактический контракт AL-TRANS создания брони и источник его подтверждения;
- какие тесты и проверки прошли;
- выполнялся ли вызов production-провайдера (ожидается: нет);
- выполнялся ли deploy и в какой версии;
- остались ли ручные действия или нерешённые риски.

Не заявлять, что функция создаёт реальную бронь, пока подтверждение AL-TRANS не проверено по фактическому контракту.
