# Задание для ИИ с доступом к Supabase: один рейс AL-TRANS и детали маршрута

Ты работаешь с Supabase-проектом BUSNET и имеешь доступ к Supabase Dashboard / Edge Functions, но можешь не иметь доступа к репозиторию фронтенда. Нужно проверить и при необходимости обновить развернутую Edge Function `altrans-adapter`, чтобы поиск отдавал один рейс, а клиент мог показать достоверные остановки этого рейса.

## Контекст

- В проекте уже существует Edge Function `altrans-adapter`. Ранее сообщалось о версии 11 с включённым `verify_jwt`; перепроверь актуальные состояние, версию и полный исходный код перед изменениями.
- У функции есть операции `routes`, `route-details`, `sync-catalog`, `search-trips` и `create-booking`. Сохрани их поведение и не удаляй операции.
- Текущий `search-trips`, согласно предыдущей проверке версии 11, возвращает `{ providerError, trips: [...], searchedAt }`, где `trips` — массив плоских результатов без `stops`.
- Требуемое поведение интерфейса: **не показывать список альтернатив**. На поиске должен быть один выбранный рейс; его детали должны содержать упорядоченные остановки с корректными датами и временем.
- Обновлённый фронтенд может читать `trip` и `trip.stops`. Старый опубликованный фронтенд может по-прежнему читать `trips`. Поэтому ответ нужно сделать обратно совместимым.
- В существующей таблице `provider_route_schedule_stops` есть `stop_order`, `day_offset`, `departure_time` и `place`, но отдельного времени прибытия в ней нет. Не выдавай `departure_time` за время прибытия.

## Сначала исследуй — ничего не меняй до проверки

1. Получи актуальный полный исходный код развернутой `altrans-adapter`. Не делай вывод о содержимом функции только по номеру версии или статусу.
2. Проверь текущие сигнатуры и контракты `search-trips` и `create-booking`.
3. Проверь схему имеющихся таблиц `locations`, `routes`, `provider_route_schedules` и `provider_route_schedule_stops`, если планируешь их читать.
4. Определи по реальной структуре ответа AL-TRANS:
   - где находится список сегментов поездки;
   - какие поля идентифицируют сегмент;
   - как представлены города, станции/места, дата и время отправления и прибытия;
   - где находятся ID, цена, валюта и признак возможности бронирования.
5. Для изучения ответа используй безопасный реальный поисковый запрос без данных пассажиров. Не публикуй API-ключи, JWT, service-role key, персональные данные и необработанные секреты в логах или отчёте. Если необходимо показать пример ответа, замаскируй чувствительные значения.
6. Если для полей остановок нельзя уверенно определить структуру, не угадывай её и не деплой предположительный парсер. Сначала сообщи точные неопределённые поля и безопасный обезличенный пример, необходимый для продолжения.

## Требуемая реализация `search-trips`

### Один результат

- Функция должна выбирать и возвращать **не более одного** подходящего доступного для бронирования результата AL-TRANS.
- Отфильтруй записи, которые провайдер не разрешает бронировать.
- Если цены валидны и представлены в запрошенной валюте, выбирай минимальную цену. При равной цене используй детерминированную сортировку:
  1. более раннее время отправления;
  2. более раннее время прибытия;
  3. стабильный `trip_id` лексикографически.
- Не сравнивай цены в разных валютах. Если результаты пришли не в запрошенной валюте, следуй фактическому контракту AL-TRANS и явно укажи поведение; не выполняй скрытую конвертацию.
- Невалидная цена не должна побеждать валидную. Если все доступные к бронированию результаты не имеют пригодной цены, можно выбрать один по времени отправления/прибытия и вернуть цену `null`; не выдумывай цену.
- Если нет доступных к бронированию результатов, верни корректный пустой ответ, не создавая фиктивный рейс.

### Обратно совместимый формат ответа

Сохрани старое поле `trips` как массив максимум из одного элемента и добавь поле `trip`:

```json
{
  "providerError": false,
  "trip": {
    "trip_id": "стабильный идентификатор для create-booking",
    "carrier": "название перевозчика",
    "bus_number": null,
    "departure_city": "город отправления",
    "departure_place": "место отправления",
    "departure_date": "YYYY-MM-DD",
    "departure_time": "HH:mm:ss",
    "arrival_city": "город прибытия",
    "arrival_place": "место прибытия",
    "arrival_date": "YYYY-MM-DD",
    "arrival_time": "HH:mm:ss",
    "price": 0,
    "currency": "UAH",
    "can_book_with_payment_at_boarding": false,
    "stops": [
      {
        "city": "город",
        "place": "станция/остановка",
        "arrival_date": null,
        "arrival_time": null,
        "departure_date": "YYYY-MM-DD",
        "departure_time": "HH:mm:ss"
      }
    ]
  },
  "trips": [
    { "trip_id": "тот же ID", "stops": [] }
  ],
  "searchedAt": "ISO timestamp"
}
```

- Для отсутствующего результата возвращай `trip: null` и `trips: []`.
- Сохрани текущие `providerError`, `errorCode` и HTTP status при ошибках.
- Старый клиент, читающий `trips`, должен получить максимум один элемент. Новый клиент, читающий `trip`, должен получить тот же самый элемент с остановками.
- Не добавляй в ответ сырой объект провайдера целиком.

## Построение остановок

- Предпочтительный источник — сегменты именно выбранного `trips_sequence` из ответа AL-TRANS. Построй упорядоченный список из начала/конца сегментов:
  - для первого пункта — отправление первого сегмента;
  - для последнего пункта — прибытие последнего сегмента;
  - для пересадочных пунктов — прибытие предыдущего сегмента и отправление следующего.
- Объединяй соседнее прибытие и отправление в один пункт только если совпадают город **и** станция/место (с учётом безвредной нормализации регистра и Unicode). Если названия станций различаются или одна из них указывает на другое место, оставь два отдельных пункта: иначе можно скрыть реальную пересадку между терминалами.
- Сохраняй исходный порядок сегментов. Не сортируй остановки только по названию или времени.
- Используй дату и время, реально полученные от провайдера. Корректно сохраняй переход через полночь и разные календарные даты сегментов.
- Если AL-TRANS не даёт полный перечень сегментов, можно использовать активное расписание из Supabase только для тех остановок и полей, которые реально есть в базе. Рассчитывай дату остановки по `departure_date + stop.day_offset - origin_stop.day_offset`, проверяя порядок остановок и день недели.
- В таблице расписания есть только время отправления остановки. Не показывай его как время прибытия. Для неизвестного времени прибытия оставляй `arrival_time: null`.
- Не смешивай остановки одного только расписного маршрута с сегментами другого результата AL-TRANS. Детали должны описывать ровно выбранный рейс.
- Если полный маршрут недоступен, верни только достоверные конечные пункты либо пустой список `stops`; не генерируй промежуточные остановки.

## Согласование с `create-booking`

- Проверь, что `trip_id`, возвращаемый `search-trips`, можно повторно однозначно найти при `create-booking`. Не меняй семантику ID без необходимости.
- `create-booking` должен повторно получить актуальные данные у AL-TRANS и проверить доступность того же рейса.
- Если клиент прислал `expectedPrice` и/или `expectedCurrency`, сравни их с актуальным результатом до создания записи. При изменении цены или валюты верни подходящий конфликт (например, HTTP 409 и `PRICE_CHANGED`), не создавай бронь по неожиданной цене.
- Поля `expectedPrice` / `expectedCurrency` могут отсутствовать у старого клиента: не делай их обязательными для старого контракта, но всегда проверяй актуальную цену с серверной стороны.
- Сохрани текущую аутентификацию, проверку пользователя, запись бронирования, запись пассажиров и права доступа. Не ослабляй RLS, `verify_jwt` или проверки авторизации.
- Не создавай реальную бронь во время проверки без отдельного разрешения владельца проекта. Не отправляй тестовые/фиктивные данные пассажиров в боевой AL-TRANS.

## Ограничения Supabase и безопасности

- Секреты AL-TRANS и `service_role` должны оставаться только в серверной функции. Никогда не помещай их в ответ клиенту, SQL-миграцию, браузерный код или логи.
- Не добавляй таблицы, колонки, политики или RPC, если задача решается текущей схемой и функцией.
- Если изменение схемы действительно необходимо, остановись до его применения: объясни, какой конкретно отсутствующий факт нельзя представить текущей схемой, предложи минимальную миграцию и дождись отдельного разрешения.
- Сохрани все пять существующих операций и текущие CORS/HTTP error contracts.
- Не меняй внешний API AL-TRANS и не вызывай дополнительные операции провайдера без подтверждённой необходимости.

## Проверки перед завершением

1. Проверь синтаксис и типизацию функции инструментами Supabase/Deno, доступными в окружении.
2. Проверь ответ поиском AL-TRANS на реальном маршруте и дате:
   - `trip` либо `null`;
   - `trips.length` не больше 1;
   - `trip` соответствует единственному элементу `trips`, если он есть;
   - `stops` расположены правильно, даты и времена соответствуют ответу провайдера;
   - нет придуманных времён прибытия.
3. Убедись, что каждый из пяти `operation` продолжает обрабатываться. Не выполняй боевое `create-booking` для проверки.
4. Убедись, что бронирование повторно проверяет актуальный рейс и корректно отклоняет изменившуюся цену, не создавая запись.
5. Разверни функцию только после успешных проверок, сохрани `verify_jwt` включённым и проверь, что новая версия имеет статус `ACTIVE`.
6. После deploy повтори безопасный `search-trips` вызов и проверь уже развернутый ответ.
7. Отдельно укажи, что backend deployment не обновляет собранный frontend автоматически. Чтобы пользователь увидел кнопку раскрытия остановок, опубликованный frontend также должен читать `trip.stops` и быть отдельно собран/развёрнут.

Не заявляй, что задача полностью решена, если исходник не был успешно развернут и проверен запросом к живой функции.
