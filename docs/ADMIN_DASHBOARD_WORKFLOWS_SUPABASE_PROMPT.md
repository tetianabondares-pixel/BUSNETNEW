# Задание для ИИ с доступом к Supabase: безопасная сверка admin workflows

## Цель

Проверить, почему frontend BUSNET использует функции и таблицы из миграции
`20261121100000_admin_dashboard_workflows`, тогда как по сообщению владельца
миграция в production Supabase не применена. Подготовить безопасный и проверяемый
план восстановления; не менять production без отдельного подтверждения владельца.

## Важное ограничение

Владелец отдельно сказал, что production-миграцию можно применять только после
его явного «ок». Запрос на сборку и Git push **не является разрешением применять
миграцию или менять production Supabase**. До отдельного одобрения разрешены
только чтение схемы, migration history, функций, политик и настроек.

Git push в `main` может автоматически запустить Vercel-деплой frontend, но не
применяет Supabase SQL. Если после push Vercel опубликует frontend, а RPC из
этой миграции всё ещё отсутствуют, разделы админки могут продолжить падать.
Проверь результат Git/Vercel отдельно от состояния Supabase и сообщи владельцу
об этом расхождении; не маскируй его как успешное применение миграции.

Не раскрывай API keys, JWT, service-role key, персональные данные пассажиров или
содержимое секретных заголовков. Не создавай и не подтверждай реальные брони.

## Уже установлено в локальном репозитории

Проверь текущее состояние заново, но не игнорируй следующие результаты:

- Supabase UI на скриншоте показывает уже существующую Edge Function
  `altrans-adapter` и 11 деплоев. Скриншот не подтверждает активный исходный код
  и не доказывает применение SQL-миграции.
- В production, по предоставленному владельцем результату проверки, нет функций
  и таблиц из `20261121100000_admin_dashboard_workflows`; последняя применённая
  миграция — `restrict_update_booking_status_to_admin_roles`.
- В репозитории `20261121100000_admin_dashboard_workflows.sql` присутствует в
  Git, но её локальное наличие не означает применение в Supabase.
- Локальный frontend вызывает:
  - `get_public_admin_settings`;
  - `admin_search_bookings`, `admin_search_passengers`,
    `admin_list_support_agents`;
  - `swap_popular_route_order`, `log_admin_action`,
    `update_booking_status`, `admin_review_cancellation`;
  - `mark_admin_notification_read`, `save_passenger_interaction`,
    `admin_update_booking_passenger`, `admin_request_booking_cancellation`.
- Frontend также читает/обновляет `admin_settings`, читает
  `admin_notifications` и `passenger_interactions`; читает `admin_profiles`.
  Сверь фактические вызовы и политики в текущем frontend, не полагайся только
  на этот список.
- В рабочей миграции локально уже исправлены четыре выявленных риска:
  однократное уведомление на новую заявку; `UPDATE` только на `read_at` и только
  активным получателям с допустимой ролью; `DROP POLICY IF EXISTS` для четырёх
  повторно создаваемых политик; фильтры дат `admin_search_bookings` по timezone
  из `admin_settings` с проверкой timezone. Перед любой live-операцией сравни
  активную production-версию миграции с этим файлом.
- Прямой `pending -> confirmed` через `update_booking_status` пока остаётся
  допустимым намеренно: подтверждённая операция создания реальной брони
  AL-TRANS не реализована. Не закрывай этот переход отдельным изменением.
- `booking_expiration_minutes = 30` пока только настройка; не вводи TTL и не
  трактуй значение как утверждённое бизнес-правило.
- В рабочей копии есть и другие незакоммиченные изменения; не удаляй, не
  перезаписывай и не добавляй к миграции несвязанные файлы без указания владельца.

## Обязательные read-only проверки

1. Получи актуальную Supabase migration history и сравни с локальными именами и
   версиями файлов. Зафиксируй точную версию последней production-миграции.
2. По именам и сигнатурам проверь наличие функций, таблиц, колонок, политик,
   триггеров и прав из миграции. Не считай `Ready` у Vercel доказательством
   состояния базы.
3. Проверь frontend на текущем Git commit и назови RPC, отсутствующие в live
   базе. Отдельно укажи, какие разделы админки могут ошибаться из-за отсутствия
   схемы.
4. Сверь `update_booking_status` с локальным SQL и подтвердите актуальные роли,
   переходы и grants. Не меняй поведение без согласования.
5. Проверь порядок миграций. В репозитории файл workflows имеет timestamp
   `20261121100000`; владелец сообщает о применённой вручную миграции
   `restrict_update_booking_status_to_admin_roles` с более поздним timestamp.
   Не переименовывай миграции, не редактируй историю и не запускай
   `supabase db push --include-all` вслепую. Предложи точный порядок, сверив
   версии локально и в production.
6. Проверь runtime-значение `admin_settings.timezone`, если таблица существует.
   Для локальных календарных фильтров ожидается timezone сайта `Europe/Kyiv`.
   Не меняй настройку без согласования.

## Исправления, уже внесённые в локальный SQL — перепроверить при сверке

1. `notify_admins_new_booking` теперь срабатывает на `bookings` после вставки,
   то есть создаёт не более одного уведомления каждому администратору на
   booking независимо от количества пассажиров. Уведомление использует номер
   заявки и статус, без копирования имени пассажира.
2. Политика редактирования уведомлений требует совпадения получателя и активной
   роли `super_admin`, `admin` или `support`. Табличный `UPDATE` отозван;
   authenticated разрешён только `UPDATE (read_at)`.
3. Перед созданием политик routes, locations, provider schedules и schedule
   stops добавлены соответствующие `DROP POLICY IF EXISTS`.
4. `admin_search_bookings` переводит локальные даты начала и исключительную
   верхнюю границу в timestamptz через timezone из `admin_settings`, по умолчанию
   `Europe/Kyiv`, и явно отклоняет невалидную timezone.

Проверь, что определения, порядок выполнения, имена таблиц/полей и права
соответствуют именно production-схеме. Не утверждай, что миграция применена,
пока не увидишь её в production migration history и не проверишь созданные
объекты.

## Запрещённые действия без отдельного одобрения

- Не применять миграцию, даже если локальная сборка прошла или frontend уже
  вызывает эти RPC.
- Не запускать миграции автоматически из CI/Vercel и не использовать `db push`
  для «проверки».
- Не менять grants, RLS, триггеры, роли, booking statuses, сроки истечения или
  данные в live базе.
- Не делать live `create-booking`, подтверждение/отмену брони и другие внешние
  операции AL-TRANS.

## Отчёт и критерии завершения

Верни владельцу:

- точную production migration history и подтверждённое состояние перечисленных
  функций/таблиц/policies/triggers;
- перечень RPC, которые сейчас вызывает frontend, и какие из них отсутствуют;
- оценку воздействия на рабочую админку и минимальный безопасный порядок
  восстановления;
- проверку timestamp-порядка, включая необходимость/ненужность
  `--include-all`, обоснованную фактической history;
- результат review четырёх локальных исправлений;
- явное подтверждение, что production не изменялась.

Остановись после read-only проверки и плана. Жди отдельного явного одобрения
владельца перед применением SQL в production.
