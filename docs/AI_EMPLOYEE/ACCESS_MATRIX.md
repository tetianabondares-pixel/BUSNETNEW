# BUSNET Digital Employee — Access Matrix

**Версія:** 0.3 · **Дата:** 2026-11-26 · **Стан:** технічна специфікація
**Пов’язані документи:** [реєстр інструментів](./TOOL_REGISTRY.md), [реєстр знань](./KNOWLEDGE_REGISTRY.md), [життєвий цикл задач](./TASK_LIFECYCLE.md)

## Модель доступу

Доступ до дії цифрового співробітника — це перетин трьох перевірок:

1. Активна сесія BUSNET та активний запис `admin_profiles`.
2. Роль поточного користувача має право викликати конкретну дію відповідно до серверного endpoint/RPC.
3. Політика помічника дозволяє цей рівень ризику; якщо потрібне схвалення — існує чинне підтвердження саме цього snapshot.

Права з інтерфейсу, підказки, системний prompt і сам факт наявності інструмента не є авторизацією. Кожен виклик перевіряється знову на сервері. RLS обмежує рядки за власником/отримувачем і активною роллю. Service-role credentials доступні лише захищеному серверному середовищу.

Матриця нижче відображає локальні політики/функції репозиторію, а не перевірений live стан Supabase. Перед активацією інструментів потрібно звірити застосовані production-міграції.

## Рівні ризику та схвалення

| Рівень | Приклади | Політика |
|---|---|---|
| `read` | Підсумок, пошук бронювань, читання маршрутів | Без підтвердження, якщо поточний адміністратор має право. Повернути тільки мінімальні потрібні дані. |
| `sensitive_read` | Пасажирські контакти, журнали з персональним контекстом | Доступ лише за роллю; мінімізувати поля й обсяг; аудіювати звернення. Масовий експорт не дозволений у першій версії. |
| `reversible_write` | Позначити власне сповіщення прочитаним, призначити відповідального | Явна команда адміністратора; окреме підтвердження, якщо зміна зачіпає чужу роботу. |
| `high_impact_write` | Статус/скасування бронювання, зміна даних пасажира, синхронізація, будь-яка розсилка чи фінансова операція | Завжди потрібне окреме підтвердження користувача з відповідною роллю. Автономне виконання заборонено. |

У першому релізі жоден записовий інструмент не має режиму «виконати автоматично». Навіть якщо користувач уже дав загальну інструкцію, конкретна дія високого ризику вимагає підтвердження.

## Рівні автономності BUSNET

| Рівень | Дозволені дії | Обмеження |
|---|---|---|
| 🟢 `green` | Пошук, аналіз, read-only перевірки, звіти та внутрішнє планування | Можна запускати вручну або з попередньо дозволених тригерів; застосовуються мінімізація даних, ліміти й аудит. |
| 🟡 `yellow` | Зміна контенту/налаштувань або виправлення низького ризику | Лише за конкретним versioned policy з обмеженими цілями, середовищем і вікном дії. Якщо правило не затверджене або вплив не можна чітко обмежити — зупинити й запросити підтвердження. |
| 🔴 `red` | Фінанси, скасування та інші критичні зміни бронювання, масові розсилки, безпека/авторизація, публікація змін | Кожна конкретна операція потребує активного адміністративного підтвердження snapshot. Заборонено запускати автономно чи покладатися на попередню загальну згоду. |

У початковому rollout усі write-інструменти лишаються `approval required`; автоматичний `yellow` не вмикається, доки окремо не буде затверджено політику, тестову перевірку, rollback і обмеження. Автоматичне виправлення коду може працювати лише в ізольованій тестовій гілці/середовищі; публікація змін у бронюваннях, платежах, авторизації чи безпеці завжди `red`.

## Approval Snapshot

Підтвердження прив’язується до незмінного snapshot:

- ID і версія інструмента;
- нормалізовані параметри та цільові ID;
- підсумок впливу: кількість записів/одержувачів, перехід стану, diff або preview;
- hash канонічного snapshot;
- user ID, дата схвалення й термін дії;
- одноразовий ключ виконання.

Якщо змінилися параметри, набір цілей, вміст повідомлення, версія інструмента або snapshot застарів — підтвердження анулюється і треба показати новий preview. Виконання зберігає user ID того, хто схвалив. Схвалення не замінює серверну перевірку ролі чи RLS.

## Власність даних і аудит

- Початковий scope задач, розмов і особистих інструкцій — власник: `owner_id = auth.uid()`. Перевірена Knowledge Base має окремий явний shared/module ACL; її доступ не означає спільного доступу до приватних інструкцій або задач інших адміністраторів.
- Повідомлення, snapshot, кроки й події задачі доступні тільки її власнику/дозволеним аудиторам за окремою політикою.
- Записові дії мають містити actor, tool/version, target, request/task ID, approval ID та підсумок зміни в audit log.
- Не зберігати access token, service-role key, документи пасажирів чи повні платіжні реквізити в prompt, task event або trace.
- Зміни ролей, активності адміністратора, RLS чи інструментального доступу не можуть виконуватися самим помічником.

## Доступ до Knowledge Center

| Дані/операція | Головний співробітник / workers | Адміністратор / Knowledge Curator |
|---|---|---|
| Спільні перевірені знання | Читати лише релевантний модулю піднабір у межах ролі та task scope. | Переглядати за дозволеною роллю; зміни версіонуються й аудіюються. |
| Доменні знання | Читати за `department`/роллю; не переходити в інший домен лише через запит користувача. | Перевіряти знання лише для модулів, наданих Knowledge Curator ACL. |
| Особисті інструкції та вподобання | Використовувати лише власника поточної задачі, якщо він їх явно активував. | Не переглядати приватні записи іншого адміністратора без окремого дозволу. |
| Нові знахідки та досвід | Створювати тільки `new`/`needs_verification` з джерелом, версією та task ID. Не активувати. | Підтвердити, відхилити, позначити stale/conflict або створити нову версію. |
| Бізнес-правила | Читати лише `verified`; не створювати дієве правило самостійно. | Підтвердження/активація — явна curator дія з audit trail. |
| Документи | Доступ до індексованих дозволених фрагментів; без довільного Storage listing/download. | Завантаження/перегляд за роллю та ACL документа; bucket приватний, операції журналюються. |

До запровадження окремого ACL Knowledge Curator ця роль не виводиться автоматично з посади `admin`; початковим власником перевірки є `super_admin`/власник BUSNET. Обліковий запис worker не отримує права змінювати власника, scope, required roles, status чи джерело знань.

## Автоматична робота та звернення до власника

- Подієві та планові запуски дозволені тільки для зареєстрованих `triggerPolicy` і green інструментів. Кожна подія має dedupe/rate limit; red-дії ніколи не запускаються автоматично.
- Важливі проблеми й approval requests створюють події/сповіщення з рівнем критичності. Низький пріоритет збирається у дайджест або звіт; пороги мають бути налаштовувані, щоб не спамити адміністратору.
- Щоденні/періодичні звіти містять лише підтверджені метрики й завершені перевірки. Прогноз, припущення та пропозиція позначаються окремо від факту.
- Одержувачі-пасажири й зовнішні адресати — окремий consent/communication scope. Адмінська роль не є дозволом на масову розсилку чи доступом до будь-якого каналу зв’язку.
