# BUSNET Digital Employee — Knowledge Registry

**Версія:** 0.3 · **Дата:** 2026-11-26 · **Стан:** технічна специфікація
**Пов'язані документи:** [архітектура та стан агента](./ARCHITECTURE_ROADMAP.md), [реєстр інструментів](./TOOL_REGISTRY.md), [матриця доступу](./ACCESS_MATRIX.md), [життєвий цикл задач](./TASK_LIFECYCLE.md)

## Мета

Реєстр знань описує BUSNET так, щоб координатор міг вибирати лише відомі інструменти з дозволеними параметрами. Реєстр — перевірена довідка, а не автоматичний доступ до вихідного коду чи бази. Знання не є гарантією, що операція доступна в конкретному production середовищі: права та дані завжди перевіряються окремо.

## Формат запису

Кожен запис має містити:

| Поле | Опис |
|---|---|
| `key`, `version`, `status` | Стабільний ID, версія, стан `new`, `needs_verification`, `verified`, `stale_or_conflict`, `rejected` або `archived`. |
| `category`, `scope` | Категорія Knowledge Center і видимість: `shared`, `module` або `owner`. |
| `department`, `module` | Відділ і модуль BUSNET. |
| `summary`, `entities`, `relations` | Перевірений опис, відомі сутності та їхні зв’язки. |
| `capabilities` | ID інструментів із [реєстру інструментів](./TOOL_REGISTRY.md), не довільні endpoint-и. |
| `constraints` | Бізнес-правила, дозволені переходи, рольові та безпекові межі. |
| `sources`, `evidence` | Посилання, уривок/результат перевірки, тип джерела й checksum/version джерела. |
| `task_id`, `supersedes_id` | Задача-відкриття/використання та зв’язок з попередньою версією або суперечливим записом. |
| `source_revision`, `verified_at`, `verified_by` | Версія джерела, дата й людина, яка перевірила знання. |
| `created_by`, `owner_id`, `valid_from/to` | Хто/який процес запропонував запис, власник приватного scope і строк актуальності. |

## Незалежність та зберігання

Knowledge Base належить BUSNET, а не головному роботу чи мовній моделі. Канонічні знання, версії, provenance, стан перевірки, зв’язки та досвід зберігаються у версійованому шарі даних Supabase; оригінали документів — у приватному Supabase Storage з окремою ACL. Стабільний Knowledge API є єдиною точкою читання для координатора, модулів і workers.

Технічні описи, tool contracts і системна карта залишаються у Git під code review. З них можна формувати knowledge records, але Git source revision зберігається разом із записом. User-uploaded документи, задачі й досвід не кладуться в локальну папку застосунку. Будь-які embeddings/full-text indexes — похідний індекс, який можна відновити з канонічного запису, а не єдине місце зберігання.

Заміна головного співробітника або підключення локальної моделі не змінює ID, версії, джерела, ACL чи історію знань.

## Джерела знань і перевірка

Кожна сутність позначає джерело:

1. `owner_input`: інструкція, пояснення, завантажений документ або виправлення адміністратора.
2. `platform_source`: затверджена документація, code/schema inventory чи результат дозволеного read-only інструмента.
3. `task_experience`: результат задачі, помилка, перевірка якості або схвалений підсумок.

| Статус | Значення та відображення |
|---|---|
| `new` 🔵 | Знайдено нове знання; ще не перевірено, тому не використовується як правило. |
| `needs_verification` 🟡 | Є джерело/доказ, але потрібна перевірка людиною чи незалежним інструментом. |
| `verified` 🟢 | Джерело й формулювання перевірені; запис може входити до відповідного retrieval scope. |
| `stale_or_conflict` 🔴 | Джерело застаріло або є суперечність; запис виключено з автоматичного застосування до вирішення. |
| `rejected` | Перевірку не пройдено; зберігається причина для історії, не використовується. |
| `archived` | Витіснено новою версією або більше не актуальне; історія збережена. |

Працівник може сам збирати факти, шукати серед доступних джерел, зіставляти їх і створювати `new`/`needs_verification` записи. Це не робить припущення бізнес-правилом. Перевірка порівнює джерело, дату, scope, наявні записи й суперечності; бізнес-правило стає активним лише після явного підтвердження уповноваженим Knowledge Curator.

## Карта BUSNET та залежності модулів

Ціль — інвентаризувати весь проєкт: публічний сайт, кабінети, ролі, базу, booking flow, маршрути/розклади, інтеграції, фінанси, аналітику й операційну підтримку. Це не означає, що всі області вже досліджені або що помічник має доступ до них. Для кожного модуля реєструвати вузли й перевірені зв’язки:

- `depends_on` / `affects`: зміна розкладу чи маршруту може впливати на рейси та існуючі бронювання;
- `reads_from` / `writes_to`: конкретні таблиці, RPC або зовнішні системи, з позначенням read/write;
- `owned_by` / `requires_role`: відповідальна доменна роль і необхідний доступ;
- `validated_by`: тести, серверна перевірка чи reconciliation для результату.

Початкові відділи: `operations.bookings`, `operations.passengers`, `operations.carriers`, `operations.routes`, `analytics`, `systems`; `marketing`, `social_media` та `email_campaigns` зарезервовані на майбутнє. Спільна пам’ять BUSNET містить лише перевірені загальні знання; доменні знання належать спеціалізованому модулю. Персональні вподобання, інструкції та контекст задачі залишаються окремо власницькими.

Автоматичне «сканування всього сайту» має відбуватися як контрольований inventory/build-time процес: збирати метадані маршрутів, типізованих модулів, schema/RPC-описів і тестів у reviewable diff. Runtime не виконує довільний вихідний код, SQL або запити по всіх даних. Нові/змінені джерела створюють `new`/`needs_verification`, а не автоматично `verified`.

## Не підтверджене / не доступне наразі

У перевірених локальних джерелах не знайдено готових інструментів чи підтвердженої моделі даних для:

- повних профілів перевізників і перевірки документів;
- профілів агентів та їхніх комісій;
- реєстру платежів/фінансів;
- health-check усіх BUSNET сервісів;
- маркетингу, соцмереж і email-кампаній;
- накопичення та оцінки результатів кампаній.

До появи джерела істини й окремої дозволеної операції ці запити мають відповідати уточненням/відмовою, а не вигаданими цифрами чи результатами. Перш ніж активувати кожну область, провести окремий інвентар даних, бізнес-правил і повноважень.

## Надходження та життєвий цикл знань

1. Нове знання додається з конкретним джерелом: endpoint/RPC, міграція, тест, документація власника або код модуля.
2. Знання порівнюється з наявними записами; дубль зливається через посилання, суперечність переводить обидва записи у review.
3. Фіксуються scope, ролі, чутливість, строки актуальності, source revision/checksum і хто/що створило запис.
4. `verified` вимагає джерела та підтвердження; правила/інструкції — явного схвалення curator-а. Інші `new` записи залишаються видимими, але не впливають на планування.
5. Застарілий або змінений source переводить запис у `stale_or_conflict`, а не видаляє історію.
6. Версія моделі/координатора не володіє знаннями; заміна її не видаляє й не переписує records.
7. Після змін модуля пов’язані вузли `affects`/`depends_on` і knowledge entries можуть вимагати повторної перевірки; невідповідність створює задачу, не змінює права чи бізнес-дані.

## Навчання на досвіді та контроль якості

Результат задачі, помилка, виправлення користувача й перевірений звіт можуть стати джерелом пропозиції нового знання. Запис має вказувати початкову задачу, фактичний результат, незалежну перевірку, модуль, дату й автора підтвердження. Корекція відповіді не стає постійною інструкцією без явного підтвердження користувача. Нове правило створюється як пропозиція; активує його відповідальний адміністратор після review і тесту.

Модулі можуть мати власні quality checks: наприклад, звірка маршруту з розкладом або перевірка агрегатів звіту повторним read-only запитом. Статистика успішності рахується з реальних перевірених запусків; неперевірені висновки та автоматичні припущення не показуються як набуте знання.

## Зв’язок з виконанням та Knowledge Evolution

Перед планом координатор отримує з Knowledge API лише дозволені `verified` знання за модулем, роллю й задачею; всі workers застосовують ту саму базу, але кожен зберігає власний task scope та tool permissions. Кожен task step/event посилається на ID і version знань, фактично використаних для пошуку чи рішення. Це дає відповідь «які правила/джерела були використані» та дозволяє відтворити попередній результат після оновлення знань.

Knowledge Evolution показує реальні агрегати з історії версій: кількість за статусом і категорією, покриття модулів, записи створені/перевірені/відхилені за період, конфлікти, stale записи та задачі, де знання застосовувались. Кількість записів не є показником якості сама по собі.

## Документи

Документи завантажуються користувачем із дозволеною роллю у приватний bucket. Зберігати checksum, тип, розмір, власника, ACL і результат перевірки; задавати whitelist типів/розмірів і безпечне вилучення тексту. Оригінал не стає доступним усім workers автоматично: Knowledge API повертає тільки дозволені індексовані фрагменти з цитатою на документ і сторінку/позицію, якщо це підтримується.

## Початковий формат знань

```ts
type KnowledgeEntry = {
  key: string;
  version: number;
  status: "new" | "needs_verification" | "verified" | "stale_or_conflict" | "rejected" | "archived";
  category: "busnet_knowledge" | "business_rule" | "experience" | "learned_knowledge" |
    "document" | "technical_knowledge" | "problem_solution" | "proposal";
  scope: "shared" | "module" | "owner";
  department: string;
  module: string;
  summary: string;
  entities: string[];
  relations: string[];
  capabilities: string[];
  constraints: string[];
  sources: Array<{ path: string; symbol?: string }>;
  evidence: Array<{ sourceType: string; sourceRef: string; checksum?: string }>;
  taskId: string | null;
  supersedesId: string | null;
  sourceRevision: string;
  verifiedAt: string | null;
  verifiedBy: string | null;
};
```

Цей контракт описує майбутній формат і сам по собі не створює runtime-сканер або дозвіл на виконання.

## Стан візуального прототипу

Поточний Knowledge Center у робочому просторі BUSNET Assistant працює з версійованими записами Supabase через рольові RPC та RLS. Старі локальні записи браузера можна імпортувати окремою дією; `localStorage` не є канонічним сховищем. Імпорт або наявність запису не робить його перевіреним автоматично.

Приватне object storage для документів, автоматичне навчання та зв’язок із workers не реалізовані. У Production залишаються 10 раніше створених пакетних записів, помилково позначених `verified`; їхній вміст — плани, а не підтверджені правила BUSNET. Потрібне окремо погоджене виправлення збереженням аудиту; не використовуйте ці записи як доказ реалізованих можливостей.
