# BUSNET Digital Employee — Task Lifecycle

**Версія:** 0.3 · **Дата:** 2026-11-26 · **Стан:** технічна специфікація
**Пов’язані документи:** [реєстр інструментів](./TOOL_REGISTRY.md), [матриця доступу](./ACCESS_MATRIX.md), [реєстр знань](./KNOWLEDGE_REGISTRY.md)

## Принцип

Задача є серверною сутністю незалежно від того, чи створена вона з чату, голосу, моніторингу або майбутнього планувальника. UI показує збережений стан і фактичні події координатора. Повідомлення «аналізую», відсоток прогресу або завершення без події/результату сервера не допускаються.

## Стани та переходи

```text
received → planning → queued → running → succeeded
                  ↘ needs_clarification
running → awaiting_approval → queued → running
running → retry_wait → queued
running → failed | recovery_required | cancel_requested → cancelled
queued  → cancel_requested → cancelled
```

Велике доручення координатор може зберегти як parent task і розбити на child tasks/steps із залежностями (DAG). Незалежні задачі стартують паралельно; крок-залежність не починається, доки її prerequisites не успішні. Часткові результати й невдалі гілки зберігаються окремо, parent завершується лише після визначеного планом узгодження.

| Стан | Значення |
|---|---|
| `received` | Команду прийнято і збережено з власником/джерелом. |
| `planning` | Визначаються відомий намір, параметри та дозволені інструменти. |
| `needs_clarification` | Не вистачає параметрів або впевненість нижча за заданий поріг; виконання не починається. |
| `queued` | План перевірено, усі потрібні approval є; задачу можна забрати worker-у. |
| `running` | Worker має чинну lease і виконує конкретний крок. |
| `awaiting_approval` | Задача зупинена до окремого підтвердження конкретного snapshot. |
| `retry_wait` | Тимчасова помилка; очікується дозволений повтор. |
| `succeeded` | Усі кроки завершені та результат записаний. |
| `failed` | Невиправна помилка або вичерпано безпечні спроби. |
| `recovery_required` | Після переривання невідомо, чи відбувся side effect; автоматичний повтор заборонений. |
| `cancel_requested`, `cancelled` | Скасування запитано; worker завершує поточну безпечну межу й фіксує, що саме вже відбулося. |

Тільки серверний координатор змінює стани виконання. Користувач може скасувати задачу або підтвердити очікувану дію, але не може напряму перевести її у `succeeded`.

## Дані й події

Рекомендовані сутності Supabase:

- `assistant_conversations`, `assistant_messages` — канали взаємодії; власник, роль повідомлення, текст і час.
- `assistant_tasks` — власник, джерело, початковий запит, нормалізований intent, поточний стан, пріоритет, план, підсумок, помилка, `idempotency_key`, timestamps, retry counters та cancellation request.
- `assistant_task_steps` — упорядкований інструмент і версія, нормалізований input, статус, спроби, checkpoint, безпечний результат і помилка.
- `assistant_task_events` — append-only журнал для timeline: `received`, `plan_created`, `step_started`, `step_completed`, `approval_requested`, `retry_scheduled`, `error`, `cancel_requested`, `completed`.
- `assistant_approvals` — actor, незмінний approval snapshot/hash, expiry, одноразовий ключ і час використання.
- `knowledge_entries`, `knowledge_versions`, `knowledge_evidence`, `knowledge_documents` — довготривала BUSNET база знань, незалежна від assistant/model lifecycle; оригінали документів у приватному Storage.
- `assistant_memory` / `assistant_instructions` — окремо від тимчасових запитів і спільної перевіреної KB; див. [реєстр знань](./KNOWLEDGE_REGISTRY.md).

Task/step/event/approval записи успадковують власника задачі й захищаються RLS. Worker-використання службових повноважень відбувається лише на сервері та має окремі перевірки ролі й задачі. Довготривале зберігання raw PII у trace не допускається.

Перед кожним task plan Knowledge API повертає лише доступні перевірені записи для конкретних модулів. Кожен step фіксує ID/version знань та документних фрагментів, які фактично використав. Знахідка під час роботи створює knowledge proposal з джерелом і task ID; вона не змінює активні правила. Всі workers читають спільну verified KB, але не спільні приватні інструкції власників задач.

## Пріоритет і черга

- Початкові значення: `low`, `normal`, `high`, `urgent`; типове — `normal`.
- Планувальник сортує за пріоритетом, а при рівності — FIFO. Потрібні ліміти на паралельність і fairness, щоб низький пріоритет не голодував.
- Система не підвищує пріоритет для обходу approval або доступу. Право користувача змінювати пріоритет — окремий доступ.
- Черга має переживати перезапуск UI й worker. Вибір реалізації (Supabase Queue/PGMQ чи власна таблиця + довгоживучий worker) перевірити проти реально доступних extensions та хостингу перед розробкою. Браузер не є worker-ом.
- Один головний координатор керує pool-ом worker slots; workers — процеси виконання без окремих чатів/пам’яті. Паралельність адаптується до черги, доступних ресурсів і rate limits. Початковий configurable cap — 3–5 одночасних workers, остаточне значення визначається навантажувальним тестом.
- Обмежувати глобальну й per-tool/per-provider паралельність, розмір пакетів, час і пам’ять. Масове звернення до пасажирів розкладається на невеликі незалежні jobs, але кількість прийнятих запитів не обмежується кількістю активних workers.

## Ручні, подієві та планові задачі

Усі джерела використовують той самий lifecycle:

- `manual`: запит адміністратора з чату, голосу чи інтерфейсу;
- `event`: зареєстрована подія BUSNET (наприклад, нове звернення або помилка синхронізації);
- `scheduled`: контрольований періодичний моніторинг, звіт чи планова перевірка.

Тригер зберігає тип/ID джерела, dedupe key, policy version і причину створення задачі. Event/scheduled jobs обмежуються allowlist-ом інструментів, порогами, частотою й ресурсним бюджетом. Пасажирський response worker активується лише після інтеграції каналу, дозволу на контакт і перевірених шаблонів; він не може надсилати масові повідомлення без red approval.

## Паралельне виконання та видимість операцій

Live Operations Center показує головного координатора як єдиного співробітника й таблицю його активних worker-процесів: worker ID, модуль, task/child task, крок, стан, час, retry та помилка. Кожен task timeline зберігає фактичні події:

- прийнята команда та визначений intent;
- використаний Knowledge Entry/tool/version і коротке структуроване пояснення вибору;
- джерело, фільтри/параметри пошуку, агрегована кількість отриманих результатів;
- початок/кінець обробки, перевірки якості, маскований підсумок і помилки;
- залежності між child tasks, approval/cancel/retry та результат.

Не зберігати прихований chain-of-thought. Показувати перевірювану трасу дій, джерел і стислих причин; чутливі поля маскувати. Replay відтворює хронологію з `assistant_task_events`, а не запускає задачу повторно.

## Самоконтроль, якість і проактивні задачі

- Self-check запускається лише через окремо визначені read-only health/test tools; він не змінює власні дозволи чи конфігурацію.
- Результат проходить зареєстровані quality checks до `succeeded`. Перевірка не пройдена — `failed` або `recovery_required`, з причиною та частковими результатами.
- Моніторинг і денне/тижневе планування створюють звичайні `event`/`scheduled` задачі, які можна переглянути й зупинити. Пороги та розклад версіонуються.
- Важливі інциденти та очікування підтвердження надсилаються негайно; низький пріоритет групується у дайджест. Кожне повідомлення має джерело, severity й дедуплікацію.
- Щоденні звіти й Evolution Center рахують лише реальні події, перевірені результати, збережені інструкції та погоджені знання. Не показувати вигадані «вивчені модулі», відсотки чи успішність.

## Виправлення помилок BUSNET

Виявлення помилки може запустити діагностичну задачу, граф залежностей модулів, тестову перевірку й підготовку ізольованого patch/branch. Автоматичне розгортання не входить до початкових повноважень. Зміни, що зачіпають бронювання, платежі, авторизацію чи безпеку, а також будь-який production release, потребують owner approval; результат тестового середовища й план rollback показуються в approval snapshot.

Механізм планування відокремлюється від виконання: детермінований engine працює без зовнішнього AI API. Майбутня локальна модель може запропонувати intent/plan, але серверний validator, tool registry, access matrix, queue та approval gates залишаються обов’язковими.

## Recovery, retry та idempotency

1. Worker отримує lease з `lease_owner`, `lease_expires_at`, heartbeat і лічильником спроб.
2. Після кожного кроку зберігається checkpoint до переходу на наступний крок.
3. Після рестарту прострочені leases відновлюються лише після перевірки стану останнього кроку.
4. Автоматичний retry дозволений тільки для класифікованої тимчасової помилки та інструмента з `retryClass = safe`/ідемпотентною поведінкою; початковий ліміт — до 3 спроб з exponential backoff і jitter.
5. Ключ ідемпотентності стабільний для конкретної задачі й кроку та зберігається унікально. Handler має повертати той самий зафіксований результат при повторі.
6. Для зовнішнього side effect потрібна підтримка idempotency ключа провайдером або власний журнал намірів/результатів. «Exactly once» без співпраці системи не гарантується.
7. Якщо невідомо, чи провайдер/база прийняли side effect, задача переходить у `recovery_required`; спочатку reconciliation або ручне рішення, а не blind retry.

## Підтвердження та скасування

- До запуску записової дії координатор зупиняється в `awaiting_approval` та формує точний snapshot: tool/version, параметри, список/кількість цілей, preview/diff і наслідки.
- Після підтвердження зміна будь-якого параметра, цілі, версії чи вмісту анулює approval. Схвалення протерміноване або вже використане — недійсне.
- Скасування кооперативне: worker перевіряє `cancel_requested` між кроками. Уже відправлений зовнішній запит не вважається скасованим, доки не отримано підтвердження від зовнішньої системи.
- Кожна зміна стану й рішення зберігається як незмінна подія та проходить перевірку доступу з [матриці доступу](./ACCESS_MATRIX.md).

## Реальний Live Execution

Realtime-підпис фільтрується за дозволеною задачею. UI показує час сервера, статус кроку, фактичний результат/помилку, спроби та очікування approval. Прогрес можна показати як `завершено кроків / всього кроків`, тільки якщо план уже затверджений і кількість кроків стала; штучний відсоток під час планування заборонений.

## Умови готовності першої версії

- Новий worker після перезапуску відновлює безпечну задачу з останнього checkpoint.
- Повтор ідемпотентного кроку не створює дубль.
- Неоднозначний або неавторизований запит не потрапляє у виконання.
- Будь-яка зміна потребує чинного approval snapshot і залишає audit-подію.
- Події Live Execution відповідають записам у БД; немає синтетичних повідомлень і фальшивих метрик.
- Перевірені сценарії з двома власниками доводять, що задачі, розмови, приватні інструкції та live-події ізольовані RLS; доступ до shared/module Knowledge Base перевіряється окремо за ACL.
